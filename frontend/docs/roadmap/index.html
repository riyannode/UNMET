Future implementation

Planned capabilities that connect funded demand to discoverable, purchasable services.

PROPOSED — NOT IMPLEMENTED

The stages below describe planned functionality, not working APIs or deployed contracts. Current capabilities remain listed in Overview.

Automatic x402 validation

PROPOSED — NOT IMPLEMENTED

Gate 0 would check a builder endpoint's unpaid x402 challenge before escrow submission and issue a short-lived signed attestation. A new immutable escrow version would enforce acceptance while preserving existing-demand settlement/refund access. Approved payment profiles would define supported networks, assets, and compatible prices.

Compatibility would not prove paid execution, service quality, or supporter approval. New submissions could depend on validation availability; eligible settlement and refunds would remain independent.

Machine-readable RFQ

PROPOSED — NOT IMPLEMENTED

Phase 1 would let agents read structured requirements and prepare unsigned demand-creation transactions. Larger technical schemas would use integrity-checked content references, while onchain economic terms remain authoritative. Historical demands would stay readable.

Service Registry

PROPOSED — NOT IMPLEMENTED

Phase 2 would publish services originating from fulfilled demands with onchain provenance. Builders could update authenticated service metadata without rewriting settlement history. Publication, compatibility, availability, and technical verification would remain separate states.

x402 Service Discovery

PROPOSED — NOT IMPLEMENTED

Phase 3 would help agents find services by capability, payment constraints, and recent observations. Purchases would go directly to the provider's authorized receiver. Optional external distribution, including OKX.AI, would require separate publication and acceptance; discovery would never authorize spending.

Intelligence Expansion

PROPOSED — NOT IMPLEMENTED

Phase 4 would add demand history, fulfillment metrics, and attributed service-usage evidence. Provider declarations, observed payments, provider-attested execution, and independent tests would have distinct evidence levels. Payment alone would not count as proof of correct execution.

Capability Resolver

PROPOSED — NOT IMPLEMENTED

Phase 5 would search compatible published services first, then matching funded RFQs, before offering unsigned demand creation. It would not spend funds, approve a service, or submit a transaction automatically.

Availability and order

The planned order is validation, RFQ, registry, discovery, intelligence expansion, then resolver. Earlier capabilities provide data and safeguards for later stages. No release date is promised. Support for additional payment networks or methods requires separate review; it is not implied by an external library's capabilities.
