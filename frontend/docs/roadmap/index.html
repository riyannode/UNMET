Roadmap and status

Implementation status and future plans for demand and services.

MIXED IMPLEMENTATION AND PROPOSALS

These statuses describe repository scope, not release acceptance or current availability. See the API reference for supported interfaces.

Automatic x402 validation

IMPLEMENTED — SOURCE/INTEGRATION

G0.1-G0.5 source and integration implement unpaid x402 challenge validation and signed attestation for the canonical escrow. G0.6 release acceptance requires independent target-host and end-to-end evidence for each release.

Compatibility does not prove paid execution, service quality, or supporter approval. Eligible settlement and refunds remain independent of validation availability.

Machine-readable RFQ

IMPLEMENTED — MINIMAL RFQ V1

Phase 1 uses a minimal versioned description in the existing demand specification. Official frontend and API creation share trimmed JCS serialization. GET /v1/demands remains discovery; POST /v1/demands/prepare returns unsigned transaction data. Economic terms remain onchain and historical specifications stay readable. No external documents or dedicated RFQ resources are planned for G1.

Service Registry

IMPLEMENTED — G2

The public Services directory and free API show canonical fulfilled demand records and cached unpaid observations. External distribution is the builder's responsibility.

x402 Service Discovery

IMPLEMENTED — G3 CORE DISCOVERY

Services can be filtered by capability, exact payment identity and recent observation state. Discovery does not authorize spending or establish paid execution. Builders manage any external publication themselves.

Intelligence Expansion

IMPLEMENTED — G4 REDUCED SCOPE

Paid intelligence includes market snapshots, coverage-gated event history and discovery metrics. All four usage evidence producers remain unsupported; expected calls are not measured usage.

Capability Resolver

DEFERRED — DEMAND-DRIVEN; NOT IMPLEMENTED

Phase 5 would search compatible published services first, then matching funded RFQs, before offering unsigned demand creation. It would not spend funds, approve a service, or submit a transaction automatically.

Availability and order

G2, G3 and G4 are usable without the resolver. Actual agent and client demand must establish future matching semantics; there is no current resolver API or commitment to a specific contract. No release date is promised. Additional payment networks or methods require separate review.
