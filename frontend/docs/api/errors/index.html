Errors & recovery

Correct invalid requests and resolve uncertain outcomes before authorizing another payment.

HTTP errors

HTTPMeaningClient action
400Invalid JSON, filters, key, or authorization.Correct the request; do not retry unchanged invalid input.
402Payment required or authorization not accepted.Inspect PAYMENT-REQUIRED. A challenge is not a receipt.
409Retained authorization/key conflict or uncertain settlement.Observe or investigate the existing operation. Do not re-sign to bypass it.
413 / 415Body too large or unsupported media type.Use an application/json object no larger than 32 KiB.
429Rate limit reached before payment verification.Respect Retry-After. Default per-IP limits are 60 demand reads and 20 intelligence requests per 60 seconds; instance settings can differ.
503Dependency, capacity, readiness, or payment storage unavailable.Retry an unsigned request after recovery. Investigate any ambiguous signed attempt first.

Error format

Normal API failures use the format below. Readiness failures also include ok: false. Official x402 challenge/payment bodies retain their protocol format; do not assume every 402 body uses this error object.

CodeMeaning
INVALID_JSON, INVALID_SORT, INVALID_STATUS, INVALID_LIMITCorrect the documented body/filter constraints.
IDEMPOTENCY_KEY_INVALIDKey must be 1–128 printable non-space ASCII characters.
IDEMPOTENCY_CONFLICT, PAYMENT_ALREADY_RESERVEDThe operation or authorization is already bound; no paid-response replay.
PAYMENT_RECONCILIATION_REQUIREDSettlement is ambiguous and requires investigation.
PAYMENT_STORAGE_UNAVAILABLE, PAYMENT_UNAVAILABLEThe service cannot safely accept payment.
RATE_LIMITED, OVER_CAPACITY, CHAIN_RPC_UNAVAILABLEBack off or wait for dependency/capacity recovery.

Recover an uncertain payment

  1. Preserve the method, path, validated request body, idempotency key, request ID, and any transaction hash.
  2. Do not create a fresh authorization after a timeout, ambiguous 503, or reconciliation conflict.
  3. Ask the service operator to investigate the existing operation. There is no public UNMET recovery endpoint.
  4. Recovery checks payment status and canonical transaction evidence. It does not submit settlement again or retrieve the original paid response.

A missing hash or contradictory evidence can leave an operation unresolved. A fresh payment is a separate spending decision, not a safe automatic retry. Share diagnostic identifiers with the operator, not private keys or raw payment authorizations.

Wallet action failures

For a rejected wallet prompt, retry only intentionally. If the account or network changes before signing, review the action under the correct session. After broadcasting, track the existing transaction even if the wallet disconnects.

A successful receipt followed by a failed state readback is not permission to fund again. Refresh the onchain view first. Native wallet-modal disconnect-pending behavior has known limitations; verify the intended wallet and network before each action.
