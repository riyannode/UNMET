# UNMET frontend

Current frontend behavior is described here. See [PRD](PRD.md) for the current demand model, [Future Implementation](FUTURE_IMPLEMENTATION.md) for proposed plans and phase status, and [Design](DESIGN.md) for UI conventions and acceptance targets.

UNMET is a market for unmet AI-agent demand. Supporters commit the configured escrow token (faucet USDC_TEST in the reviewed Testnet configuration) to capabilities; builders submit services for weighted approval or rejection. Only explicit approver funds settle. Other eligible commitments remain refundable.

This interface serves demand funders and builders comparing capability, escrow, calls, price and review state. The app uses route navigation and a shared shell; Create Demand uses a deterministic guided chat and six-term review. The wizard preserves the existing Reown wallet, receipt, readback and action rules and uses the canonical contract path only after explicit create intent. Its responses are local UI prompts, not AI-generated content.

The standalone landing page is at /. App routes /market, /market/:chainId/:contract/:demandId, /create-demand, and /analytics share the ReUI sidebar. Navigation is Explore Market, Create Demand, and Analytics. Demand Details keeps Explore Market active. Selecting a market request from the board or Analytics opens its dedicated Demand view with Request Details, Escrow & Support, and Builder Proposal tabs. The Create Demand wizard collects service capability, specification, maximum unit price, expected calls, initial escrow and deadline, then offers review, edit and Create & Fund Demand controls. The demand actions are labeled Support This Request and Submit Service Proposal; contract function names remain unchanged.

The standalone `/services` list searches loaded results; `/services/:chainId/:contract/:demandId` shows service identity, fulfillment provenance, offers and cached unpaid observations. The builder proposal flow collects receiver, network and request inputs, requests signed builder authorization, verifies the signed validation PASS in the frontend, then requests separate wallet approval for the attestation-gated transaction. Analytics reads market data directly from the contract; it does not consume paid G4 intelligence.
